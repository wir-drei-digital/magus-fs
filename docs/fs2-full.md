# FS2-A full native folders

A configured native folder runs background capture, publication and incoming regular-file application through `magus-fs sync run --state STATE --serve true`. Use `magus-fs sync status --state STATE` for separate local/private/shared progress, current live state and `native` readiness/displacements. The same private owner control channel serves these commands while the daemon runs.

Start with ordinary files whose bytes and mapped metadata match the attached view; Core verifies that inventory before watching. Mismatched initial files fail closed. Initial directory materialization is a separate operation, and this application path does not force a remote tree over an arbitrary existing directory.

Native `notify = 8.2.0` events schedule scans after100ms; a scan runs every2s and immediately at startup or after overflow. Events never suppress capture by pathname or elapsed time. Incoming authenticated metadata/log polling runs every1s even without WSS hints. Capture/admission, publication and incoming advancement share `SyncExecution`; Core's mutex is not held across remote fetches. A capture interrupted before queue admission is re-enqueued with its original operation and attached base before capturing a later generation. Existing pending descriptors are never rebased.

Core remains the only journal, capture, permission and native-application owner. Files are ordinary filesystem files and remain usable after the owner process exits. A full folder cannot revoke access to plaintext already available through the host filesystem; remote authority checks protect Core and service operations, not offline direct OS reads.

## Application contract

`Replica::apply_native_revision(&RevisionId, u64, OperationId, Actor)` and `apply_native_view(SyncBinding, u64, OperationId, Actor)` return `Result<NativeApplyStatus, FsError>`. Status is `Ready { revision }`, `Pending { reason }`, `Unstable { reason }`, or `ApplyBlocked { reason }`. Current native state and retained displacement paths are available through `native_status()` and the active verification operation `scan_native_status()`.

Regular-file creation and content exchange beneath existing directories keep the per-file path below. Every other change (directory creation, removal or move, file rename or deletion, type replacement, a new identity at an existing path, root/directory/file mode or mapped ownership changes) uses the structural root exchange described in the next section. A missing expected file is not deletion authorization. Root and directory identity checks use no-follow directory descriptors. Per-file staging is in the replica's private control directory, outside content, and must be on the same device. Unsupported exchange/no-replace primitives fail without overwrite fallback.

The intent and original generation precede the filesystem mutation. macOS uses `renameatx_np` with `RENAME_SWAP`/`RENAME_EXCL`; Linux uses `renameat2` with `RENAME_EXCHANGE`/`RENAME_NOREPLACE`. The displaced native generation stays in private staging. Its baseline observation and digest come from the same read that verified the old canonical bytes; later observations cannot silently replace that verified baseline. Its identity, metadata and bytes, the installed target, and the final folder inventory are checked before committing the native baseline, working revision, binding and any matching applied receipt in one SQLite transaction. No hard links join writable generations. A racing unexpected displacement is retained and cannot become Ready. Recovery uses the original operation/generation and never unlinks a replacement it cannot identify as its own.

## Structural application by verified root exchange (FS2-B)

A structural change stages a complete new root beside the bound root, as `<parent>/.<root>.magus-<operation>` on the same filesystem, and exchanges the two directories with the same OS primitive (`renameatx_np(RENAME_SWAP)` on macOS, `renameat2(RENAME_EXCHANGE)` on Linux). The journal records, before any mutation, the bound parent and root inode identities, the generation, the complete pre-exchange inventory (every entry's observation and the digest of every regular file) and the identity of every staged entry. Phases are `Staging → Prepared → Exchanged → Verified → Ready`; a failure before the exchange marks the intent `Abandoned` without changing the bound root. Immediately before the exchange the parent, root and stage identities and the complete inventory are re-verified; there is no stat-then-overwrite fallback and no hard link joins generations.

After the exchange the displaced root, now at the stage name, must match its pre-exchange inventory exactly and the installed root must consist of exactly the staged identities and target content. Any difference retains both roots, marks the intent ambiguous, copies each differing file into owner-private storage with a recovery record, and reports `ApplyBlocked { ambiguous_root_exchange | unowned_target_replacement }` without advancing readiness. Crash recovery compares the inode identities at the root and stage names with the durable phase: unexchanged work continues, an exchange that completed before its journal write is recognized, and any other combination is retained as ambiguous. A replaced bound root or parent before the exchange (`bound_root_changed`, `bound_parent_changed`) abandons the intent and never mutates the unowned replacement. The displaced root is never removed or overwritten; it is enumerated as the `""` displacement in `native.displacements`.

Capture-excluded ordinary entries (outside the selected policy) are copied into the staged root as opaque local-only content: regular files and directories only, never following links, preserving bytes, mode and owner. A symlink, special file, hard link, extended metadata or a non-preservable owner blocks (`unsupported_local_entry`, `mapping_blocked`); an unreadable local subtree blocks as `unreadable_local_entry`; an incoming managed path that equals, contains or lies inside a local-only entry blocks as `local_entry_collision`. A root whose parent is not writable reports `readonly_parent`; a root on a different device from its parent reports `cross_device`; a filesystem without directory exchange reports `exchange_unsupported`. These are explicit `ApplyBlocked` states; all work is retained and user files are never relocated or rewritten to make an application fit. Ownership is mapped through the configured authorities and checked before staging with the POSIX change rule (an owner may only change the group to one of its groups; a non-root process cannot give a file away).

A full copy is the deliberate cost of structural changes; ordinary content saves keep the chunk-efficient per-file path. The existing admission limit applies: a structural application is admitted only if the current retained bytes plus the original root and the staged root fit within 512 MiB and the retained generations (each displaced root counts as one, each copied version as one) stay within 128; otherwise `displacement_backpressure` is reported and nothing is staged. Descriptors held by other processes can still grow retained files beyond this estimate; the next scan reports the pressure.

A successful exchange changes the root inode. The watcher compares its armed root identity with the verified baseline identity after every scan and re-arms on the installed root (`native_watch_rebound` in the owner log) and rescans. A pathname whose identity is not the verified root is never adopted by the watcher; periodic scans keep observing it. Descriptors and working directories that still reference the displaced root write into the retained root and remain periodically discoverable.

## Retained alternatives and explicit recovery

Every scan rescans retained displaced files and roots. A changed or new regular file is copied into the replica's private stage directory before its observation advances, and an immutable `NativeRecoveryRecord { id, operation, original_base, source_path, observed_generation, observed_digest, causal_coverage }` is created (`observed_generation` is the local generation the original application expected; `observed_digest` is `sha256:` of the retained copy). Native displacement alternatives always have `causal_coverage: Unknown`; `RecordedBase` is reserved for retained work whose base is proven. The status reports `Pending { late_displaced_write }`, clears applied readiness and blocks later applications as before. Records survive owner restart; changed retained bytes always produce a new record and never rewrite an old one.

```sh
magus-fs sync recovery list --state STATE
magus-fs sync recovery capture --state STATE --id RECORD_ID --digest sha256:... --operation-id operation:...
magus-fs sync recovery export --state STATE --id RECORD_ID --digest sha256:... --destination /absolute/new/path
```

The commands use the live owner socket when an owner runs, and are selected only by opaque 32-hex record id plus the expected digest; no raw pathname is a selector. Listings are bounded to 128 records. `capture` verifies the current retained bytes against the selected digest (`generation_mismatch` if they changed, `operation_mismatch` for a wrong digest or a reused operation), requires the path to be selected by the bound capture policy, authorizes against current authority (the authenticated remote projection, else the current working tree; revoked or remotely removed identities are denied, historical metadata never authorizes), creates a new attributed local revision whose only parent is the record's original base and whose tree carries current metadata, whose coverage is the record's path and whose provenance is `native_unknown_causality` for unknown causality, and links it immutably to the record. It never changes the working head, the queue or the source record and never integrates; replaying the same operation returns the same revision. `export` writes the verified bytes to a fresh destination with `O_EXCL` (never overwriting; refused inside the private state). Readonly owners refuse `capture`. Recovery bases and captured revisions are GC roots. Journal schema 2 adds the record tables by an in-place additive upgrade; binaries that only know schema 1 fail closed with `unsupported_schema`.

## Unknown causality

`native_unknown_causality` is a fixed provenance token (accepted by the descriptor validator alongside `explicit`, `native_scan_delete_create` and `engine_observed`; the canonical encoding is unchanged). Besides recovery captures, a native capture carries it when it changes the native generation (identity, size, times, mode or owner) of a regular file that a native application installed and whose next native change has not yet been captured. Committing an application records those files durably (journal table `native_applied`); an unchanged re-observation by a capture of other paths does not clear a row, only a capture that records a change of that path (or a later application of it) does. Engine-applied paths come from the durable application record, never from names or timestamps, and lookup errors fail the capture instead of defaulting to known causality. Typical case: an editor that read bytes before an incoming update saves its stale RAM afterwards, even after unrelated saves were captured. The first native change of an applied file is therefore conservatively unknown even when the editor did reread it.

Ruling R6: a candidate whose revision carries this token never integrates automatically into a shared branch, not even as a fast-forward. The client submits it privately, then holds it in `PrivateRemote` with `error: "unknown_causality"`; `sync drain --level shared` reports `unknown_causality`, and other queued submissions continue. While held in a `shared-live` binding the candidate is unresolved, so incoming application waits (local bytes are never overwritten). Only an explicit `sync integrate --revision R --expected-head H`, or later explicit recovery (FS2-B Task 2), can publish it.

Application of multiple files is sequential. Ordinary programs may observe a mixture during application; this is not an atomic directory snapshot. Readiness verifies the current pathname generation at the observation boundary. It does not promise that another process lacks a stale file descriptor or cached RAM buffer, or that a subsequent write cannot occur.

## Capture and retained writes

`capture_native_changes(OperationId, Actor)` rescans without relying on event delivery. It skips a new checkpoint only when native identity/metadata and verified bytes match the baseline. An in-place save retains its canonical EntryId; an unknown atomic-save replacement keeps FS1 delete/create semantics. A verified application commits new native identities against the accepted canonical IDs, avoiding an echo checkpoint.

`scan_native_status()` scans retained displaced inodes as well as current content. A late old-FD write clears applied readiness, marks unknown causality and copies an observed version into a separate retained file. An unresolved retained write blocks a later application from making a new Ready claim. These separately addressable pending alternatives retain their original application operation, path and version paths across owner restart. Every persisted native status rebuilds this enumeration from durable intents, including when a later application is rejected. That operation links to the durable original base, native generation and canonical EntryId in the owner intent. They are not canonical captured revisions or private-remote receipts. Explicit promotion/reconciliation and richer conflict inspection belong to FS2-B; the engine never invents base-aware causality for an old descriptor write.

Admission stops at 512 MiB or 128 retained/staged generations instead of deleting evidence. External writers can grow an inode through an already-open FD; the next scan reports backpressure and preserves it. This is an admission/retention policy, not an OS quota on other processes. Metadata-only observation is insufficient: the Linux gate reproduced same-size writes with indistinguishable timestamps, so bytes are checked too.

`recover_native_application(Actor)` retries exact retained application intents. `verify_native_baseline(Actor)` can establish the initial observed inventory only from matching bytes and mapped metadata. Both operate through Core's existing owner. Remote fetch callbacks for application run outside its mutex, and fetched bytes are verified before cache installation and native mutation. Incoming revisions and original bases are GC roots. Existing queue records and immutable source identities are preserved.

## Reproduce the native gates

From this checkout, with the existing Rust 1.92.0 toolchain:

```sh
RUSTUP_TOOLCHAIN=stable cargo test --locked -p magus-fs-core --test native_apply --features test-faults
python3 tests/fs2/full_native.py --output /private/tmp/NEW_FULL_OUTPUT
python3 tests/fs2/full_native.py --case supplement --output /private/tmp/NEW_RESTART_OUTPUT
python3 tests/fs2/full_native.py --case retention --output /private/tmp/NEW_RETENTION_OUTPUT
```

The full harness uses macOS ordinary files and a separate unprivileged Linux client container against the actual authenticated HTTPS service, PostgreSQL and S3 fixture. It verifies dropped native hints/rescans, in-place and atomic saves, no echo or needless own-acceptance rewrite, atomic exchange/no-replace, retained late descriptor writes, owner-process crash recovery, editor/parent/symlink races, frozen dirty candidates, readonly parents and blocked directory creation. The supplemental gate verifies unchanged-endpoint transport recovery and exact retained alternatives after owner restart. The retention gate writes through a held FD at the displaced-verification/baseline barrier and checks alternative bytes, rejected-apply enumeration and owner restart on both platforms. `--platform macos|linux` selects one platform; `--case permissions` probes only readonly/structural application. Outputs must be new absolute paths. The default complete journey has a600s bound plus bounded setup/cleanup; missing prerequisites return2, failed assertions1, and success0.

All source/dependency/image/binary hashes, actual byte/status evidence, failed results and exact owned cleanup are retained by the harness. Fault instrumentation is compiled only with `test-faults`; the default binary cannot enable the omitted-event or crash barriers. `tests/fs2/native_core.py` remains an independent Core-only gate and does not substitute for the service journey.

The FS2-B native completion gate is `python3 tests/fs2/native_complete.py --platform all --output ABSOLUTE_NEW_PATH`. It runs the Core structural/recovery matrix on the macOS host (APFS) and in owned Linux containers (tmpfs, as root without capabilities and as uid 1001 with a second group), the watcher rebind test on both, real owner-process journeys against the authenticated service on both OSes (structural service matrix, held descriptor/working directory across a root exchange with recovery list/capture/export and owner restart, stale RAM save, readonly root parent, root replacement before exchange, kill after exchange) and the macOS NFS live journey of [fs2-live.md](fs2-live.md). `--case` selects `core|structural|recovery|causality|races|nfs`.

The native status distinguishes Pending, Unstable and ApplyBlocked using safe error codes. A transient discovery failure clears native readiness and forces re-verification when the service recovers, including when the remote head is unchanged. This is not a claim that disconnected capture/publication or arbitrary editor recovery has been fully qualified. Disconnected reconciliation, merge of unknown-causality candidates and broader editor compatibility remain later FS2-B tasks.

The connected qualification gate in [fs2-qualification.md](fs2-qualification.md) separately measures64MiB full bootstrap and two fresh Mac/Linux journeys using source-matched release runtimes. Initial baseline hydration is bounded60s; incoming application keeps its30s aggregate hydration bound, and each remote object remains bounded4.5s. Incoming and native byte verification are unchanged. Debug regression checks remain separate from the optimized latency measurements.
