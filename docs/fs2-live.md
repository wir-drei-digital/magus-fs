# Linux live views and open epochs

Every attached Linux mount, including `isolated`, polls the authenticated durable change log and current authorized view. A separate explicitly trusted WSS connection receives cursor hints; hints are not content authority and do not hold the publication execution gate. Discovery and publication share the bounded `SyncExecution` gate, without holding Core's mutex across discovery requests. The Core journal owns incoming authority, working state, immutable sources and receipts.

```sh
magus-fs sync attach --state STATE --profile PROFILE --branch main --publication shared-live
magus-fs mount --state STATE --revision ATTACHED_PROJECTED_REVISION --mountpoint MOUNT --mode private
magus-fs sync status --state STATE
```

Use `--mode read-only` for an absolute readonly live mount. The default isolated publication mode preserves private work and does not adopt shared updates automatically. Its discovery worker still enforces authenticated current authority and credential revocation, without changing bytes, adopted epoch or Applied acknowledgement. Existing unbound FS1 snapshot mounts keep their historical behavior.

## Descriptor semantics

Each accepted remote adoption advances a persistent epoch independently of the ordinary local mutation generation. Files receive distinct native inodes per epoch; directory identities remain stable to avoid invalidating a path walk halfway through a directory lookup. Existing descriptors read the preceding epoch's bytes and size. Current identity, ancestry and permission checks still apply. A remote rename retaining the identity permits old reads under current ancestry. A remote replacement or unlink removing that identity denies old-epoch reads conservatively. Same-epoch open-unlinked, append and fsync semantics are unchanged.

Writes, truncates and handle metadata mutations from an old epoch return `ESTALE` before mutation. Readonly denial remains absolute. No implicit private branch or rebase is created. Epoch trees and their object roots remain protected while descriptors retain them. Native fsync is local durability and does not imply upload or shared acceptance.

Core adopts only clean, generation-matching state. Unresolved submissions and unsubmitted local checkpoints block replacement. A newer authority projection can revoke access while incoming content remains pending; dirty bytes and queued original bases are retained. Legitimate never-observed local creates retain their own identity and permissions, subject to the current remote parent authority. An identity once present in authenticated remote authority remains remote-known even if it originated locally and adoption was blocked. Core rebuilds an ID membership set from its immutable authority history on open and updates it after committed observations; later remote removal cannot turn that identity back into a private create. The independently journaled authority generation rejects stale observations; its immutable history records authenticated descriptor identities or definitive denial. Authentication denial closes this replica’s mounted remote access; a transient transport outage retains last-known authority. It does not disable unrelated replicas or delete retained bytes. Explicit owner-controlled local recovery/archive APIs retain their existing scope; they must remain outside the workload boundary. These controls cannot erase previously downloaded files or copies and do not replace the existing explicit local recovery/archive rules.

Every incoming source is an immutable opaque identity outside canonical content. The trusted resolver retains its original namespace, projected view and profile binding. A queued publication continues using its original binding and request digest after another view becomes active. Projected snapshots have their own canonical hashes and no parents; they are not the server's full revision DAG.

Refreshing the token file within the same immutable profile requests a fresh credential-bound view/source. A clean mount may adopt it even when the content hash is unchanged. Cached old-epoch reads still require current authority. Uncached reads through an older credential-bound source may fail conservatively after token replacement; A does not promise historical credential rebinding. Dirty content remains retained: `live.pending_revision` and `live.pending_source` distinguish pending content/source adoption from the active epoch, including same-content reauthorization. The older source is never retargeted. Broader offline/archive reauthorization and rehydration remain a B recovery consideration.

## Trusted publication identity

A privately provisioned transport profile may include `"publication_principal": "<configured principal ID>"`. It chooses the attached checkpoint/publication actor; the principal must exist in the local replica's configured authorities and the authenticated service credential must independently authorize the resulting descriptor. This field participates in the immutable transport identity, so changing it after attachment requires a new attachment. Omitting it preserves daemon-owner behavior and existing profile fingerprints.

This is an administrative provisioning choice, not a workload or wire-supplied impersonation parameter. Private-control peer authorization, per-request native UID/GID authorization, current logical rights, readonly denial and service grant enforcement remain separate. The synthetic gate provisions Alice explicitly, then runs the Python workload as uid1001 and checks its Alice-attributed checkpoint/private receipt without remapping Alice to root.

## Native readiness

Descriptor import and working-tree adoption do not assert Applied. The adapter invalidates existing inode data/attributes, old and new names, and affected directory entries through the actual FUSE notifier. It then performs ordinary kernel metadata lookups, checking current names, types and sizes and absence of removed names. Only that acknowledgement marks the adopted projected revision ready. A matching shared receipt can then expose `applied_revision`; the submitted, private, shared and projected identities stay distinct. Failed invalidation or inconsistent lookup keeps acknowledgement pending.

DefaultPermissions, direct I/O, native ownership mapping and current metadata projection remain enabled. The daemon, local control socket and transport credentials must stay outside the workload's mount/security boundary.

## macOS NFS live epochs (FS2-B)

An attached macOS loopback-NFS mount (`magus-fs mount` with a sync binding) now uses a live workspace and adopts accepted views like the Linux adapter. NFSv3 file handles are `nonce || fileid`; each fileid is issued for an `(EntryId, epoch)` pair for regular files and for a stable `EntryId` for directories, so a path walk never loses its directory handle across adoption. A new lookup after adoption returns a new fileid for each file; an old handle keeps reading its own epoch's bytes and size (GETATTR/READ through the retained epoch handle) subject to current identity, ancestry and permission checks. WRITE, SETATTR (size/mode/owner) and time changes through an old-epoch handle fail `NFS3ERR_STALE` in Core before any effect. A removed or replaced identity denies old-epoch reads conservatively when the client asks the server, as on Linux; a directory identity removed by an adopted epoch answers `NFS3ERR_STALE`. NFSv3 has no server-to-client invalidation, and the real gate observed that the macOS client can keep serving its own cached listing and file bytes to a process whose working directory is inside a remotely replaced directory without sending any request; nothing created or written through such a working directory reaches the replacement (the create fails). Unbound FS1 mounts keep epoch 0 and their same-epoch semantics (open-unlinked, replacement, fsync).

NFSv3 has no CLOSE and no server-to-client invalidation. Issued handles, and therefore their epoch trees and object roots, are retained for the daemon lifetime. Fileids are kept in O(1) maps and allocated only when a client operation names an entry (client verification never allocates). At most 128 retained epochs and 1,048,576 issued fileids are admitted; beyond either bound adoption is deferred (authority is still observed) and the owner logs `{"live_pressure":{"retained_epochs":N,"epoch_limit":128,"issued_fileids":M,"fileid_limit":1048576,"adoption":"deferred"}}`; every `live_applied` line also reports `retained_epochs` and `issued_fileids`, while `sync status` keeps reporting `live.pending_revision`. Restarting the mount daemon releases them. Adoption advances every issued directory's change time so client name caches revalidate within the mount's 1s attribute timeout.

Applied readiness is acknowledged only after the real client path is verified: the owner checks that the mountpoint is an NFS mount, then performs ordinary `lstat` calls through the kernel NFS client for every current name the fixed actor may traverse, requiring the adopted epoch's fileid, kind and size, and the absence of removed names. A failed verification keeps the adoption pending and is retried every second; success logs `live_applied epoch=... client_verification_us=...`. Opening a file for writing makes the macOS NFS client create an AppleDouble sidecar `._<name>` holding `com.apple.provenance` (qualified FS1 behaviour: an ordinary file of the workspace). On a live mount that is local dirty work, so Core defers adoption (`live_adoption_deferred code=dirty_working_state`, `live.pending_revision` set) and never overwrites it; the sidecar must be checkpointed and published (or otherwise resolved) before later accepted views are adopted. Errno contract for authority narrowing on a mount (Ruling R8): when the narrowed entry stays in the authorized projection (for example owner read-only `0400`), it remains visible and a denied operation (a write open) fails `EACCES` without creating local dirty work; when narrowing removes read authority (mode `0`), the service's authorized projection omits the entry, so after adoption a fresh lookup fails `ENOENT` and existence is not disclosed; when authority is narrowed or revoked without adopting a new view (isolated publication, credential revocation), the still-visible entry fails `EACCES`. The real gate asserts each code exactly. Isolated publication still observes authenticated authority, narrowing and revocation without adopting bytes. The fixed-actor loopback limitation is unchanged: wire AUTH_UNIX is not authentication.

`python3 tests/fs2/native_complete.py --platform macos --case nfs --output ABSOLUTE_NEW_PATH` is the real-mount journey: held descriptor fstat/read/write/fsync/close errno, held working directory, fresh-lookup visibility within 15s, structural and parent-directory replacement, mode narrowing, credential revocation/renewal and an isolated mount. It passed as part of the complete native gate (`native_complete.py --platform all`); the task report records the run, its source commit and the observed errno/epoch values. Observed on macOS 26: a stale write through an old descriptor is buffered by the client (write(2) returns 0) and fails `ESTALE` at `fsync`, with no effect on the accepted bytes; a fresh lookup saw new bytes in about 1.2–1.3s.
