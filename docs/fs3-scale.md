# FS3 bounded cache and mounted fanout

Run from this checkout with the owned local Docker fixture available:

```
python3 tests/fs3/scale.py --image sha256:IMMUTABLE_IMAGE_ID --output /private/tmp/NEW_FS3_SCALE
```

The output directory must be new and absolute. The accepted source bridge compares every actual image input and all five binaries. When reusing the older image, the only extra Core input allowed is the exact frozen `crates/magus-fs-core/tests/fs3_cache.rs` test; it is not compiled into the reused production binaries. Any different production Rust/build input rejects reuse. The existing optional Lazy principal/mapping extension and FS3 Python inputs are recorded separately. A changed test hash requires an explicit bridge update and focused proof, not a blanket test-directory exemption.

The full phase creates fresh cohorts of 1, 5 and 20 independent Linux FUSE receivers plus one Linux full-directory publisher. Each cohort shares one owned PG/S3/service stack. Ordinary UID1001 processes make three saves: a 1KiB in-place update, a 1KiB atomic replacement and a new 1KiB file. Existing full/native capture produces the candidate and Shared receipt; the harness does not author those revisions over HTTP. Every receiver needs exact head/projected revision, Applied status and fresh content SHA256. Failed and missing observations remain in the attempted/successful/failed accounting.

Each cohort declares a 600-second total fixture ceiling before starting. The existing 4.5-second missing-object retrieval and existing request/readiness deadlines remain unchanged. The harness observes publication for 15 seconds and save visibility for 30 seconds; normal fixture shutdown permits 60 seconds. The total ceiling does not enlarge any individual deadline. Partial runs and cleanup failures fail. `--replicas 1`, `5` or `20` selects a focused, explicitly incomplete run and cannot qualify the full phase.

The five-receiver cohort runs one bounded additional ordinary save while a receiver is disconnected, another owner is paused and a third credential is revoked. Healthy receivers must progress; disconnected and paused receivers must recover after resumption. A separate receiver drops WSS hints for its lifetime, using the existing fault binary to exercise durable fallback. The service fault binary enables existing transfer instrumentation only. These binaries are named in the actual binary manifest and are not production package members.

The read fixture is 4MiB, made of sixteen distinct deterministic 256KiB chunks. Cold metadata traversal, two verified 4KiB ranges, warm repetition and full scan are separate samples. Metadata/warm reads must add no authorized content transfer. Full scan verifies the entire file. Service install, backend put, backend verification and authorized content bytes remain separate; bootstrap/scripted HTTP control accounting, process CPU/RSS and object/SQLite occupancy are recorded independently. Continuous client control-body bytes are unavailable from the existing status API and explicitly reported as such. Timing counts and Docker statistics are observations, with no percentile threshold, confidence claim or throughput promise.

Successful clean prune/refetch runs before later publications can invalidate old source authority. The CLI runs only after normal unmount and owner exit. Dry-run and token apply use the real `Replica::prune`/`apply_prune` path; remount and authorized refetch must reproduce the exact large-file hash. A stale or denied source may conservatively refuse prune, retaining the content.

The focused Core test uses `ReplicaConfig.cache_bytes=12` and real disk-backed state. Queued, failed and uncertain operations retain their actual frozen request/digest, base and candidate bytes plus later dirty bytes under pressure and across reopen/prune. No pin masks the operation-base protection. Existing focused source-attributed tests separately prove held-handle/pin roots and stale-token rejection. They use one Core owner; no live prune command or second journal writer is invented. The content bound may refuse installation. It is not a bound on SQLite, metadata/history or conservative NFS roots, and does not promise automatic eviction or server-history deletion.

Raw evidence lives under each `cohort-N`: source bridge, limits, ordinary commands, receipt/status/read rows, service transfer logs, CPU/RSS/cache observations, Core proof logs and owned mount/resource cleanup. `result.json` is the phase decision. All FS3 additionally requires isolation, packaging and actual provider evidence; this phase cannot substitute for those gates.

For a runtime change, the existing Linux release recipe supports `VERIFY=0` for a build-only freeze. Its `VERIFY=client` branch runs `cargo test --all-targets`, which currently also tries to compile the path-including `client_probe` example as a test and fails on its crate-root assumptions. Keep that failure visible; the affected production binary gate is `cargo test --locked -p magus-fs --bin magus-fs --all-features`. Record the actual Linux and host counts separately. Do not alter production code or suppress source checking to repair an unrelated probe-test target.
